The reframe

Turn one reviewer’s judgment into a system.

One design-systems specialist cannot manually review work from 60+ designers. Instead, they author a rulebook the reviewer can enforce consistently.

The agent decides implementation

Did the change reuse existing APIs? Are values encoded as tokens? Does it accidentally affect other components? Is web/native parity preserved?

Humans decide design direction

Should this feature exist? Does it belong in Razorpay’s design language? Is the requirement right? Those remain product and design decisions.

How it works

Three steps, one useful answer.

The reviewer combines exact code checks with model judgment only where judgment is actually needed.

01

Read the change

It reads your intent or Git diff and finds the components, props, tokens, and values you changed.

02

Check Blade

It compares the change with Blade’s real component APIs, token graph, and written rules.

03

Give a verdict

You get one of three answers: correct, needs work, or needs a human reviewer.

Architecture

Most of the answer does not need a model.

The pipeline separates facts from judgment. Each layer has one job, and later layers cannot erase evidence produced earlier.

L0

Extract

Parse Blade source and diff-added TSX into typed component, prop, token, and JSX facts.

L1A

Prove

Run exact checks for literals, duplicates, variants, naming, parity, and cascade.

L1B

Structure

Turn an added JSX subtree into an evidence-backed plan using existing Blade components.

L2

Judge

Send only unresolved questions and relevant context to one model call.

L3

Route

Return correct, needs work, or needs human. Proven blockers always win.

The four checks

Small set, high leverage.

The POC focuses on architectural mistakes that are costly to discover late and concrete enough to verify.

Encoding

Is it represented correctly?

Find hard-coded colours and dimensions, invalid token names, misplaced component tokens, and switch-based variant styling.

Cascading

What else will change?

Trace shared tokens and base components to every consumer. Pair web and native changes by component and matching file surface.

Reuse

Does Blade already have it?

Match against base-commit tokens and variant axes. For a new component, compare its extracted prop surface with existing components.

Composition

Can existing components build it?

Read the added JSX tree, map raw containers, text, controls, lists, and tables to verified Blade primitives, and report uncovered elements.

Structure reuse, without visual guessing

section > h3 + p + button becomes Box + Typography + Button only when those components exist in the extracted Blade graph. The recommendation remains advisory because matching markup does not prove matching behaviour.

A real cascade example

Changing border.radius.medium from 12 to 8 to “fix Card” would also reshape Button, Chip, Alert, and 53 other consumers. Blade Review names those consumers and recommends a Card-local token instead.

The rulebook is the product

Every verdict points back to an agreed rule.

Rules carry an ID, severity, plain statement, examples, and a source in Blade’s RFCs or contributor guidance. A rule with no source is a rule nobody agreed to.

Why trust it

Facts first. Judgment second.

The model cannot overrule a proven code issue. When the evidence is unclear, the tool asks for a human instead of guessing.

Grounded in Blade

Component APIs and token relationships are extracted from source code.

Every issue cites a rule

A reviewer can see what failed and where the rule came from.

Safe by default

Uncertain approvals become human reviews, never silent passes.

Provider flexible

Run offline, with Anthropic, or through any model available on OpenRouter.

Routing

Three outcomes, not a forced yes or no.

The system is deliberately asymmetric: a false rejection costs one conversation; a false approval can silently damage the design system.

Correct

Pass quietly

No blocking issue and enough confidence. CI succeeds without adding review noise.

Incorrect

Block with a fix

A proven violation requests changes and can include a GitHub suggestion block.

Needs human

Defer safely

Ambiguous cases stay neutral and request the design-systems team.

CLI before the PR

Review an idea or a local patch while the implementation is still cheap to change.

CI on the PR

The same review(change) → Verdict engine posts a GitHub review, check result, and applicable fix.

Measurement

Safety is measured, not claimed.

The eval suite compares the deterministic floor with the full judgment layer. False approvals lead because they are the most expensive failure.

Hand-written goldens

Realistic positive, negative, and deliberately ambiguous cases with expected verdicts, rules, and affected components.

Graph-derived controls

Known-good Blade surfaces generate labelled negative mutations and positive config/parity controls, preventing a reject-only reviewer from hiding behind class imbalance.

Current published numbers use the offline provider in both eval arms. The harness is ready to expose the model’s actual delta once a remote provider is configured.

What the evals caught

The harness tests the reviewer—and the rules.

Evaluation is not only a model score. It exposes incorrect assumptions in the policy and implementation itself.

01 · The graph corrected the reviewer

The Button example looked like a new tertiary variant. Extraction proved that variant="tertiary" already exists, turning a subjective objection into an exact reuse violation.

02 · A test caught a policy bug

Positive controls prevent a reject-only system from looking accurate on a negative-heavy dataset. Deferrals are measured separately from real approvals.

Build versus buy

The moat is Blade-specific knowledge, not the chat model.

Limitations

What this POC does not solve yet.

The boundaries are explicit so the next evaluation round can target them.

  • Prose parsing is partly heuristic. Signals that are not backed by the graph cannot become proven blockers.
  • Cross-file prop types are not fully resolved. Local unions and intersections are handled, but imported types need a full checker program.
  • The model contribution is not measured in current results. Both saved eval arms ran with the offline provider.
  • Positive controls defer offline. The offline floor never approves by design, so its current accuracy is 77.9% and correct-approval recall is reported separately as 0%.
  • The rulebook needs team ownership. It is sourced, but production deployment starts with Blade maintainers reviewing and editing it.
  • The graph must be refreshed. Intent review is only as current as its extracted Blade release; CI rebuilds against the PR.
  • TSX structure is semantic, not visual. It uses complete JSX blocks rather than screenshots; partial prop-only hunks and subjective visual fit still defer.
