Proof of concept · Design systems

Blade PR Review Agent

An architectural reviewer for Blade component and property PRs. It decides whether a change was built correctly — and defers to a human on everything else.

The design-systems reviewer stops being the bottleneck and becomes the author of a machine-enforceable rulebook. Every verdict cites a rule; every rule cites where in the Blade repo it was agreed.

Grounded on razorpay/blade @ 4c07772 94 components 2,146 tokens 844 cascade edges 46 eval cases 22 unit tests

01 · The reframe

Design system teams have shifted from creators to checkers. Designers now raise component and property PRs directly, which is the right direction, but one design-systems person cannot meaningfully review PRs from 60+ designers — and most designers have no reason to know how to architect a new property the right way.

The instinct is to build a reviewer that reads the diff and gives an opinion. At Razorpay's scale that fails on questions any reviewer will ask: the verdicts are non-deterministic, there is no audit trail, the model's knowledge of Blade is frozen at training time, and there is no way to know whether it is actually right.

So the design starts somewhere else. The agent does not have opinions about Blade; it applies a rulebook the design-systems team owns, against a knowledge graph extracted from Blade's own source. That is what makes it scale: one person cannot review 60 designers' PRs, but one person can maintain rules a system applies to all of them, consistently, with every verdict traceable.

02 · What it decides, and what it refuses to

There are two lenses on any component PR, and conflating them is how these tools lose trust. The agent owns exactly one.

LensQuestionOwner
Subjective Does this still feel like a Razorpay button? Does it belong in our design language? Human
Objective Assuming the requirement is valid, has it been built correctly? Agent

The system prompt states this boundary explicitly: if a change is architecturally sound but the model has an aesthetic opinion about it, the verdict is correct. The agent is not a taste engine and is instructed not to behave like one.

03 · Architecture

Four layers, each one narrowing what the next has to handle. The ordering is the whole design: everything mechanically decidable is decided mechanically, so the model only ever sees the residue that genuinely requires judgment.

L0

Extraction

Parses Blade with the TypeScript compiler API into a typed graph: every token with its literal value, every component's prop unions, and the token→component edges. Regenerated per release, so the agent is never stale and no Blade fact is ever hand-written into a prompt.

L1

Deterministic checks

Decides everything mechanically decidable. Exact, free, and identical on every run — which is also what makes the cost story work, since the model never sees what this layer already settled.

L2

Judgment

One structured call with a retrieved context bundle. The validator rejects any rule id the model invents and drops any component it hallucinates. Not an agent loop — control flow stays in TypeScript where it can be read, tested and diffed.

L3

Routing

Three outcomes, not two. Deliberately asymmetric: a proven blocker cannot be approved away, and an under-confident approval becomes a deferral rather than an approval.

04 · Grounding on real Blade

Everything below was extracted from a live clone of razorpay/blade, not hand-authored. Blade turned out to be unusually well suited to this: it already ships 38 per-component token files that map prop combinations to dot-notation token paths, 67 _decisions/decisions.md API documents, and an RFC that states the architectural principles outright.

Two consumption patterns, both required

A naive extractor misses half the graph. Blade components consume tokens two different ways, and only handling both makes cascade analysis correct:

// 1. semantic tokens, as dot-notation strings in component token files // packages/blade/src/components/Button/BaseButton/buttonTokens.ts primary: { default: 'interactive.background.primary.default' } // 2. global tokens, as member access on the theme object // packages/blade/src/components/Switch/AnimatedThumb.web.tsx border-radius: ${makeBorderSize(theme.border.radius.max)}; // 3. and the hard case — a computed index borderRadius: theme.border.radius[itemBorderRadius[size]] // recorded as `border.radius.[*]`: a change to ANY radius token can // affect this component, so the group is recorded rather than the edge dropped

On over- versus under-reporting. The wildcard case is a deliberate choice. A missed consumer is a correctness failure that destroys trust the first time a designer is told “this only affects Card” and it did not. A widened group is a disclosure we can label. So the extractor widens, and says so.

05 · The three checks

Correct cascading

This is the brief's own example, run against real Blade. A designer thinks the Card corners are too round and reduces the shared radius token:

$ npm run review -- --diff radius.patch "The Card corners look too round." - medium: 12, + medium: 8,
BlockerCAS-001proven by static analysis

border.radius.medium is consumed by 57 components. Changing its value changes all of them.

Stated target: Card.
Not stated but affected: Accordion, ActionList, Alert, AppBar, Avatar, BaseMenu, Box, Button, ButtonGroup, Carousel, Charts, ChatInput, Checkbox, Chip, +43 more.
BlockerREUSE-001proven by static analysis

The proposed value 8 is already encoded by an existing token.

border.radius.small = 8  ·  tokens/global/border.ts:47
spacing.3 = 8  ·  tokens/global/spacing.ts:38
BlockerREUSE-002proven by static analysis

A global token is being changed to serve a single component. Blade's convention is to start local and promote only once a third consumer appears.

→ components/Card/cardTokens.ts

Getting this to fire from the diff alone required real work. A diff hunk shows medium: 8 with no nesting context, so the leaf key has to be resolved back to its addressable path by matching the file the edit landed in against the extracted index. Without that resolution step the single most important case this tool exists to catch silently passes.

Reuse over duplication

Prose intent, no diff. The agent resolves the component name against the graph, then matches the proposed value against the component's real extracted union:

$ npm run review -- "add a tertiary variant to Button with a green background #0A8000"
BlockerREUSE-003

Button already accepts variant="tertiary". This variant does not need to be created.

Button.variant allows: primary, secondary, tertiary
Extracted from source at blade@4c07772, not recalled.
WarningENC-001

Literal colour #0a8000 used where a design token is required.

No existing token holds this value — a genuinely new colour still needs a token, and REUSE-002 says where it should live.

Correct encoding

The tokens RFC opens by describing the pattern it was written to eliminate: variant styling expressed as switch branches returning values. That description is now a detector, and the rule cites the RFC section it came from.

// flagged: ENC-002 — variant styling as conditional branches switch (variant) { case 'tertiary': return isDisabled ? 'light.950' : 'light.900'; } // correct: a declarative mapping in the component token file const buttonTokens = { base: { tertiary: { default: 'surface.background.gray.intense' } } };

07 · Routing, and the asymmetry that matters

A false reject costs a designer one round trip. A false approve puts a wrong pattern into the design system permanently and silently. The two are not symmetric, so the routing is not symmetric either.

  • A proven blocker cannot be approved away by the model. That is the point of proving it, and it is covered by a unit test that feeds a confidently-wrong model response into a diff with a real violation.
  • An under-confident approval becomes a deferral, never an approval.
  • A provider failure degrades to needs_human, never to correct, and never hard-fails the build.
  • No findings does not mean correct. It means the deterministic layer had nothing to say, which is a different claim.

The third verdict state is what makes the tool honest. Routing to a human is a correct answer, not a failure — the system prompt says so explicitly, so the model is not pushed toward false confidence to look useful.

08 · Surfaces

Both surfaces are roughly fifty-line adapters over one function, review(change) → Verdict. The engine is the product; the form factor is a delivery detail, which also makes the choice reversible.

The CLI works before a PR exists. That is a real product point, not a demo convenience: catching a wrong approach at intent time costs a designer a conversation, while catching it at review time costs them a day of work and a rejection.

The CI check is where it scales to 60 designers without anyone opting in. There is no separate dashboard, deliberately — reviewers already live in the PR, so the PR is the interface:

VerdictGitHub actionCheck
correctPassing check, no comment — silence is the reward for doing it rightsuccess
incorrectREQUEST_CHANGES with the fix as a suggestion blockfailure
needs_humanComment + request review from the DS team, non-blockingneutral

Two details carry disproportionate weight. The suggestion block renders with a Commit suggestion button, so a designer who does not know the architecture gets the correct implementation applied in one click — “no, and here is the commit” rather than “no, and here is why”. And a deferral is neutral, never failure: a deferral that looks like a broken build teaches a team to ignore the check within a week.

The human loop closes back into the evals

When the design-systems reviewer disagrees, they reply /ds-agent disagree <reason> in the thread. That override is appended to evals/overrides.jsonl and becomes either a new eval case or a rulebook amendment. The reviewer still handles the uncertain cases, but their review time now compounds instead of evaporating.

09 · Measurement

This is the part that separates a system from a demo, so it is built as a first-class surface rather than a script. npm run eval reports two arms side by side, which makes the model's contribution a number rather than a claim.

False approve0.0%0 of 44 changes that should be rejected
False reject0.0%0 of 2 positive controls
Verdict accuracy95.7%n = 46 cases
Rule citation100%right answer for the right reason
Cascade recall100%deterministic by construction
Deferral rate8.7%routed to a human

Those figures are the deterministic floor — Layer 1 only, no API key, no network, fully reproducible. That matters more than a higher number would: it is the guaranteed behaviour of the system, and anyone can clone the repo and reproduce it exactly.

Metrics chosen for what they catch

MetricWhy it is reported
False approve rateLed with, not accuracy. The asymmetric cost is the entire argument for how routing works.
Rule-citation accuracyCatches a reviewer that guesses “incorrect” and happens to be right. Raw accuracy hides this completely.
Cascade recallShould be exactly 100% because it is computed, not recalled. That it is 100% is the evidence for splitting the architecture this way.
Run-to-run stability--runs 3 measures flakiness directly, rather than reasoning about whether a non-deterministic reviewer can be trusted.
Deferral rateToo high and it is useless; too low and it is overconfident. Both failure modes are invisible in accuracy.

Where the cases come from

Twelve hand-written goldens covering each rule category, including two positive controls and one deliberately ambiguous case that should defer — without those, a checker that rejects everything scores well. The other 34 come from a synthetic mutation generator that takes real, merged, correct Blade source and corrupts it in ways that map one-to-one onto rulebook violations: inline a token's value, duplicate an existing token, re-propose a variant that already exists, edit .web without .native.

That gives labelled negatives at zero labelling cost, with a distribution across rule categories we control rather than inherit from whatever PRs happened to exist. Mining Blade's real PR history — merged PRs as positives, “changes requested” PRs with the maintainer's comment as negatives with free ground-truth reasoning — is the natural next source, and is listed in the plan below.

10 · What the eval harness caught

Two findings worth reporting, because they are the argument for building the harness at all rather than shipping on vibes.

Finding 01 · the agent corrected me

I hand-wrote a case asserting that adding an elevation prop to Card was a genuinely new axis and should defer to a human. The agent returned incorrect. It was right and I was wrong: Card already declares elevation?: keyof Elevation at Card.tsx:85, so the correct verdict is REUSE-003, extend the existing prop.

The ground truth was corrected in the case file with the reasoning recorded. This is the clearest demonstration I have that grounding verdicts in extracted source beats recollection — including my own.

Finding 02 · the harness caught my own policy bug

The design has a safety rule: signals derived from prose are heuristic, so they cap at warning and never block a PR. The eval run showed that rule was too blunt — it was downgrading findings whose evidence was graph-proven, and the reuse category sat at 62.5%.

When the graph proves that Button.variant already accepts "secondary", only the wish came from prose; the component and the value are both exact matches against unions read off the AST. The fix was to the policy, not the test. Reuse went to 100% and overall accuracy from 75.6% to 95.7%.

Tightening that also introduced two false rejects — a prop mentioned in passing (“to control internal padding”) and a negation (“no new props”) were both being read as additive intent. Both are now unit-tested regressions.

11 · Implementation plan

Phases 1–5 are built and running. Phases 6–8 are what I would do next, in priority order.

  1. 01

    Extraction pipeline done

    TypeScript compiler API over a Blade checkout. Token index with literal values, component API index with prop unions, and both token-consumption patterns. Cached as a JSON artifact so a CI run costs one file read.

  2. 02

    Rulebook done

    Fifteen rules distilled from the tokens RFC, the cross-platform RFC and Blade's contributor guidance, each with a required source field and a flag for whether a deterministic check fully covers it.

  3. 03

    Deterministic checks done

    Eleven checks over a change model that normalises prose intent and unified diffs into structured signals, with the prose/diff provenance boundary enforced throughout.

  4. 04

    Judgment and routing done

    Retrieval bundle, provider interface with an Anthropic implementation and a deterministic offline provider, schema and grounding validation, and the asymmetric routing rules. 22 unit tests cover the routing invariants.

  5. 05

    Surfaces and evals done

    CLI, GitHub adapter with suggestion blocks, a workflow that rebuilds the graph from the PR's own checkout, and the two-arm eval harness with the mutation generator.

  6. 06

    Mine Blade's PR history next

    Merged designer PRs as positives; “changes requested” PRs with maintainer comments as negatives carrying free ground-truth reasoning. Target 150+ real cases so the metrics reflect real designer behaviour rather than synthesised failure modes.

  7. 07

    Override ingestion next

    Wire /ds-agent disagree through to evals/overrides.jsonl and a weekly triage that turns overrides into eval cases or rulebook amendments. This is what makes the system improve rather than plateau.

  8. 08

    Rule telemetry next

    Which rules fire most, and which get overridden most. A rule with a high override rate is a wrong rule; a rule that fires constantly marks a part of Blade designers consistently misunderstand. That is an organisational signal, not a code check.

12 · Build versus buy

I evaluated Graphify for the knowledge-graph layer. It does hybrid extraction — tree-sitter for code, LLM extraction for docs — and exposes an MCP server and an HTML visualisation, so the temptation was real.

I used the idea for the unstructured layer and rejected it for the code layer, for two reasons. First, a generic code graph yields symbol-level edges (Button.tsx imports tokens.ts), not the design-system-semantic edges the three checks actually need — resolving a styled-components template through a theme object into a specific token, indexed by component and variant, is Blade-specific modelling and is the actual IP here. Second, Graphify labels edges EXTRACTED / INFERRED / AMBIGUOUS, and for a blocking check an inferred cascade edge is a liability, not a feature.

Writing it directly against the compiler API also collapsed the dependency tree to a single runtime package — typescript, which Blade already ships. The Anthropic call is plain fetch, because a blocking CI check should own its timeout and retry policy rather than inherit them from an SDK.

13 · Limitations

Stated plainly, because a POC that claims no weaknesses is not being read carefully.

  • Prose parsing is heuristic where it is not graph-backed. This is why prose-derived signals are capped at warning unless the graph proves them. The boundary is enforced in code, but it is a boundary, not a solution.
  • Prop extraction does not resolve cross-file type references. It builds a local alias table per file and flattens unions and intersections through it, which covers Blade's actual composition patterns, but a prop type imported from another module is not followed. A full type-checker program would fix this at a real cost in extraction time.
  • The judgment layer's contribution is currently unmeasured. Both eval arms report identical numbers because no API key was available in the build environment, so the offline provider ran in both. The harness is built to show that delta; the delta itself is the first thing to fill in.
  • The two positive controls cannot pass offline. The offline provider structurally never returns correct, which is honest but means the floor's ceiling is 95.7% by construction, not by failure.
  • The rulebook is my reading of Blade's RFCs. It is sourced and citable, but a real deployment starts with the design-systems team editing it, which is exactly the intended workflow.
